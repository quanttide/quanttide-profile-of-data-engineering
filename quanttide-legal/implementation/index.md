## 技术栈与选型理由

**选 Python**，理由按本项目实际的工程重心：

1. 本项目的负载是 IO 密集而非计算密集——生产步骤的瓶颈是调用被测模型服务（网络等待）与人工研判（人的时间），不是本地算力。Python 在调度、重试、并发编排上的开发速度优势完全覆盖这个场景。
2. 研判环节需要配套的小工具（盲评子集导出、结论导入、一致率计算），数量多而每个都小，Python 的迭代速度最适合。
3. 数据处理用 polars（与仓内搜索行为分析项目同一技术栈，先例可复用）；统计检验用 numpy 手算，不引统计库。
4. CUE 校验通过调用 cue CLI 完成，schema 文件与生成器、校验器三方共用同一份。

**Rust 的启用条件**（现在不用，写明触发条件避免将来随手重写）：变体生成成为 CPU 密集瓶颈（如关键词库量纲达到属地最高档、变体规则组合爆炸），或变体规则需要与词库处理合并为独立组件交付时，将变体生成器单独抽为 Rust 组件，通过命令行与本管道衔接。主管道不因性能预期提前换语言。

代码落位：当前阶段属最小验证，实现放实验室仓 `examples/quanttide-data-lab`；触发迁移的条件是与 qtcloud-data CLI 的 spec/pipeline 命令合并需求出现时，迁入平台仓作为子命令。
