# AGENTS.md

本文件是 `project-record`（项目记录）的撰写规范。它与其他产品档案不同——本档案的**核心用途是复盘**：把真实数据项目做完后，复盘业务经验，沉淀成可开源的数据工程资产。

## 概览

`project-record` 是「案例式项目」的复盘载体，用真实项目反哺开源。每个项目一个目录，遵循「日志是事实唯一来源，档案从日志萃取」的链路。随迭代更新、反映当前理解，不追求一次写全。

## 与其他产品档案的区别

| | 其他产品档案（qtcloud-product 等） | 本档案（project-record） |
|---|---|---|
| 目的 | 想清楚「这个产品要做什么」 | 复盘「这个真实项目做完了什么、沉淀出什么」 |
| 视角 | 产品级思考（定位/核心目标/阶段方法/数据驱动/需求与AI） | 项目复盘（数据本身 + 项目上下文 + 开源沉淀） |
| 产出 | 产品规划 | 工作手册、教程、README、工具 |

## 目录结构

```
project-record/
├── AGENTS.md         # 本文件：项目记录撰写规范
├── index.md          # 项目档案（通用模板）
├── requirement.md    # 需求地图（通用模板）
└── <project-name>/   # 每个真实项目一个目录
    ├── <date>.md     # 项目日志（事实来源）
    ├── index.md      # 项目档案（从日志萃取）
    └── requirement.md # 需求地图
```

## 项目档案（index.md）

从以下层面记录：

### A. 项目本身（数据工程视角）

- **定位** — 真实项目 → 数据工程开源的桥梁
- **核心目标** — 用案例式项目反哺开源
- **阶段方法** — 五阶段项目制 + 复盘闭环
- **数据结构** — 真实项目沉淀的字段、口径、命名规范
- **数据质量** — 从真实项目「用」出来的质量口径

### B. 复盘与开源（核心用途）

- **业务经验** — 真实问题 + 解决方案
- **可复用结构** — 能抽象的字段口径、流程、标准
- **开源产物** — 工作手册、基础教程、README、工具

### C. 项目上下文

- **来源** — 谁委托（脱敏后仅保留「客户委托的学术/商业项目」等泛化描述）
- **交付要求** — 交付什么、验收标准（脱敏，不写具体数字）
- **时间线/状态** — 当前进度、关键节点

## 需求与复盘档案（requirement.md）

- 用「明确性检验」：能写出字段口径就是明确的，写不出就是模糊的。
- 内容聚焦：字段、口径、质量约束。
- 每个项目结束后，把复盘出的「可开源资产」补进「复盘与开源」小节。

## 脱敏约定（重要）

对外开源前必须脱敏，遵守以下规则：

- **客户身份**：不出现客户姓名、机构、学校、公司等可识别信息
- **对接人**：不出现团队成员的姓名
- **核心字段口径**：不出现具体字段名（用「实体名称」「匹配 ID」「扩散计数」等泛化词）、精确数字（行数、样本规模）、窗口边界等
- **数据库名**：不出现具体金融/商业数据库名（CRSP、Compustat 等）
- **可保留**：公开数据源（如 USPTO、GitHub 这类公开平台）、处理方向（名称标准化、模糊匹配、fork 统计、合并拆分）、方法论（CLI 复现、spec 约束、复盘经验）

原则：**只保留「什么网站/数据源 + 做了哪方面的处理」，核心字段和精确口径一律模糊掉。**

## 约定

- 命名：项目目录用英文名（如 `uspto-entity-matching`、`github-activity-panel`），正文能用中文用中文；专有名词与缩写保留原文（CLI、Provider、Studio、DRD、Contract、Blueprint）。
- 事实来源：项目目录下的 `<date>.md` 日志，档案从日志萃取提炼。
- 档案随迭代更新，反映当前理解，不追求一次写全。
